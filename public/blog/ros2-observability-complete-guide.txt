# ROS2 Observability: A Complete Guide

Running ROS2 robots in production requires more than just writing good code. You need to know what's happening inside your robots at all times. That's where observability comes in.

## What is Robotics Observability?

Observability is the ability to understand the internal state of your robot systems by examining their external outputs. For ROS2 robots, this means collecting and correlating:

- **Logs**: Textual records of what happened and when
- **Metrics**: Numerical measurements of system behavior over time
- **Traces**: Request flows through your distributed robot systems
- **Events**: Significant occurrences like mode changes, errors, or sensor readings

**Why Observability Matters**
Without proper observability, debugging a robot failure becomes a guessing game. With it, you can pinpoint exactly what went wrong and why in minutes instead of hours.

## The Three Pillars for ROS2

### 1. Logging

ROS2's `rclcpp` and `rclpy` provide built-in logging through `RCLCPP_INFO`, `RCLCPP_WARN`, and similar macros. However, effective logging requires:

- **Structured logging**: Use key-value pairs for machine-parseable logs
- **Correlation IDs**: Link related log entries across nodes
- **Appropriate levels**: Use DEBUG for development, INFO for normal operations, WARN/ERROR for issues

```python
self.get_logger().info(
    'Navigation goal reached',
    extra={'goal_id': goal_id, 'duration_ms': duration}
)
```

### 2. Metrics

Key metrics to track for ROS2 robots:

| Metric Category | Examples |
|----------------|----------|
| System Health | CPU usage, memory, disk I/O |
| ROS2 Specific | Topic latency, message rates, QoS mismatches |
| Navigation | Path length, replanning frequency, localization confidence |
| Application | Mission completion rate, error counts |

### 3. Traces

Distributed tracing becomes crucial when debugging cross-node issues. Track the journey of:

- Navigation goals through the Nav2 stack
- Sensor data from drivers to consumers
- Commands from high-level planners to actuators

## Setting Up ROS2 Observability

### Step 1: Centralized Log Collection

Don't rely on SSH and `journalctl`. Set up centralized log collection that:

- Aggregates logs from all robots in your fleet
- Provides full-text search capabilities
- Allows filtering by robot ID, node, severity, and time range

### Step 2: Metrics Pipeline

Implement a metrics pipeline that:

1. Collects metrics at regular intervals (typically 1-10 seconds)
2. Stores time-series data efficiently
3. Provides visualization and alerting capabilities

- Collection Interval: < 100ms (For real-time visibility)
- Retention Period: 30 days (For trend analysis)
- Alert Latency: < 5s (For fast incident response)

### Step 3: Alerting

Configure alerts for critical conditions:

- CPU or memory exceeding thresholds
- Topic message rates dropping below expected values
- Sensor health degradation
- Navigation failures or excessive replanning

**Alert Fatigue**
Be selective with alerts. Too many false positives lead to alert fatigue where real issues get ignored. Start with critical alerts only and expand carefully.

## ROS2-Specific Considerations

### Topic Monitoring

Monitor these aspects of your ROS2 topics:

1. **Publication rate**: Is data flowing at expected frequencies?
2. **Message latency**: How long from publish to subscribe?
3. **QoS compatibility**: Are publishers and subscribers using compatible QoS settings?
4. **Buffer usage**: Are messages being dropped due to full buffers?

### Node Lifecycle

Track node state transitions for managed nodes:

- Unconfigured → Inactive → Active
- Unexpected transitions may indicate issues
- Correlate lifecycle events with failures

### TF Tree Health

The TF tree is critical for navigation. Monitor:

- Transform availability
- Transform age and staleness
- Missing links in the transform tree

## Best Practices

### 1. Correlate Everything

When an incident occurs, you need to see:

- What logs were generated at that time
- What metrics looked like before and during
- What changed in the system (deployments, config changes)

### 2. Make Debugging Self-Service

Engineers should be able to investigate issues without needing:

- SSH access to production robots
- Help from the "one person who knows the system"
- Hours of manual log correlation

### 3. Proactive Monitoring

Don't wait for failures. Set up monitoring for:

- Sensor drift detection before it causes navigation failures
- Battery degradation trends
- Network connectivity issues
- Resource usage approaching limits

**Pro Tip**
Set up dashboards for each robot type showing key health indicators. Review these daily to catch trends before they become incidents.

## Common Navigation Failure Types

Before diving into debugging, understand the failure modes:

| Failure Type | Symptoms | Common Causes |
|-------------|----------|---------------|
| Path Planning Failure | No path found | Blocked goal, incomplete map, costmap inflation |
| Localization Loss | AMCL confidence drops | Feature-poor environment, sensor issues |
| Recovery Behavior Loop | Stuck in spin/backup cycle | Narrow passages, dynamic obstacles |
| Goal Timeout | Mission times out | Slow planning, excessive replanning |

## The Debugging Process

### Step 1: Reproduce and Capture

The biggest challenge with navigation failures is that by the time you investigate, the robot has moved on. You need:

1. **Continuous recording**: Log all relevant data, not just when failures occur
2. **Event markers**: Automatically flag navigation failures in your logs
3. **State snapshots**: Capture costmaps, TF trees, and sensor data at failure time

<Callout type="tip" title="Pro Tip">
Configure your robots to automatically capture extended logs (10 minutes before/after) when navigation failures occur. This context is invaluable.
</Callout>

### Step 2: Check the Basics First

Before deep-diving, verify these fundamentals:

```bash
# Check TF tree connectivity
ros2 run tf2_tools view_frames

# Verify localization is running
ros2 topic echo /amcl_pose

# Check costmap updates
ros2 topic hz /global_costmap/costmap
```

Common issues that cause mysterious failures:

- **TF timeouts**: Transforms becoming stale
- **Clock sync**: Timestamps misaligned between nodes
- **QoS mismatches**: Messages being dropped silently

### Step 3: Analyze the Timeline

Navigation failures rarely have a single cause. Build a timeline:

1. When did the failure occur?
2. What was the robot's state 30 seconds before?
3. Were there any sensor anomalies?
4. Were there deployment changes that day?

## Specific Failure Debugging

### Path Planning Failures

When the planner returns no path:

1. **Check the goal pose**: Is it actually reachable? Inside walls or obstacles?
2. **Examine costmap inflation**: Over-inflated costmaps can make valid paths seem blocked
3. **Verify map accuracy**: Does the map match reality?

```python
# Key parameters to check
costmap_2d:
  inflation_radius: 0.55  # Too high = narrow passages blocked
  cost_scaling_factor: 3.0  # Affects path proximity to obstacles
```

<Callout type="warning" title="Common Mistake">
Don't just increase the inflation radius when robots hit obstacles. Find out why localization or sensing is inaccurate first.
</Callout>

### Localization Failures

AMCL losing track of position:

1. **Check particle cloud spread**: Wide spread = uncertainty
2. **Verify sensor data quality**: LiDAR returns, odometry drift
3. **Examine environment changes**: Did something move since mapping?

Key metrics to monitor:

- AMCL covariance values
- Scan matching scores
- Odometry vs. AMCL drift

### Recovery Behavior Loops

Robot stuck in endless recovery:

1. **Check recovery behavior sequence**: Is it appropriate for the situation?
2. **Verify controller timeout settings**: Are they too aggressive?
3. **Examine local costmap clearing**: Are phantom obstacles persisting?
